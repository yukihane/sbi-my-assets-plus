# SBI証券 My資産に運用成績を表示する UserScript 実装計画

利用者が通常どおりSBI証券にログインし、My資産の資産推移画面で「更新」を押し、円貨入出金明細CSVを選ぶと、**資産の増減のうち、外部からの資金移動を除いた金額**を確認できるようにする。これを最初のリリース（MVP）の利用手順とする。

MVPの対象環境は、Windows 11上のFirefoxとGoogle Chromeの両方とする。どちらもTampermonkeyを使用する。TypeScriptで開発し、依存ライブラリを含む共通の `.user.js` を1本配布する。方式選定の経緯は[構想メモ](./design.md)を参照。

## 1. 最初の作業 — 取得できるデータと画面の確認

対象画面は `https://site.sbisec.co.jp/account/assets`、観測済みの読取先は同一オリジンの `GET /account/api/assets/valuations`。保存した応答では `balances` の各行が「Unix時刻（ミリ秒）、円評価額」の組で、金額は同じキーの `valuationsTransitions[t].ALL.valuation` と一致した。評価日は日本時間に変換する。照合時の集計対象は4種類から選ぶ。預り金の除外には `balancesWithoutDeposit`、iDeCoの除外には `balancesWithoutIdeco`、両方の除外には `balancesWithoutDepositAndIdeco` を使う。各系列の金額は、対応する除外条件の `valuationsTransitions` 系列の `ALL.valuation` と照合済み。開発版は利用者が選択したファイルから評価額を読み取る。評価日の締め時刻と入出金の対応、サイトからの直接取得、グラフ直下の挿入位置は引き続き確認する。

円貨入出金明細CSVには照会条件の前置きと合計欄があり、その後に「入出金日・取引・区分・摘要・出金額・入金額」の表が続く。片側がゼロの金額欄、照会条件による絞り込み、摘要と区分の組み合わせを考慮して実明細用アダプターを実装する。実ファイルはGit管理外の `realdata/` に置く。

| 優先順 | ログイン済みの対象ブラウザーでの確認手順 | 実装に渡す結果 |
|---|---|---|
| 1. 資産推移 | 開発者ツールの「ネットワーク」を開いてMy資産の資産推移を表示する。`valuations` で絞り、表示期間を変えて要求と応答を比較する。日付を一つ選び、応答中の合計・内訳を画面の同日表示と突き合わせる。 | 要求先・必要な引数、日付・評価額のキーと型、単位、円換算、評価時点、粒度、取得範囲、欠損表現を記録する。キー構造を残し値を架空にした最小の応答例を作る。 |
| 2. 入出金明細 | 円貨入出金明細で期間を指定して照会し、次ページやCSV出力時の通信も確認する。CSVをローカルで開き、文字コード、ヘッダー、日付の意味、入出金欄、摘要、識別子、同一内容の複数行を確認する。 | 架空のCSV例と実際の摘要に対応する分類表を作る。直接取得の可否、期間上限、全ページを取得したと判断できる条件を記録する。取引ゼロの日と履歴を取得していない日を区別できるよう、照会の対象期間を控える。 |
| 3. 画面への組み込み | 開発者ツールの要素検査で既存グラフの親要素を確認する。画面を往復し、期間変更や再描画でコンテナが入れ替わるかを観察する。 | 挿入位置の目印と対象URLを決める。Shadow DOM内の仮パネルをグラフ直下に一度だけ表示し、既存のナビゲーションや期間変更が機能することを確認する。 |

公式ガイドによると、資産推移の評価時点は原則として毎週土曜日の朝7時で、全評価額がゼロの場合には例外がある。日次終値を仮定すると、評価日当日の資金移動を誤った週に含める可能性がある。実口座用アダプターでは、応答の日付と明細の反映基準を照合してから集計に渡す。[SBI証券「資産の推移を確認する」](https://search.sbisec.co.jp/v2/popwin/guide/tool/assets/02_assets/chart.html)

評価対象の境界もここで確定する。国内・米国株式、投資信託（NISA分を含む）、円貨・外貨預り金、金銀プラチナ、iDeCo、連携銀行預金の各項目について「合計に含む／含まない／未確認」と根拠を記録する。対象内外をまたぐ振替や外貨の入出金を円貨明細だけで捕捉できるかも調べる。捕捉できない場合は、その影響を受ける期間を完全な集計として扱わない。

内部APIのプログラム利用に関する利用規約を確認してから、通常の認証済みセッションで、利用者の操作を起点に評価額を読み取れるかをUserScriptで試す。必要な実行コンテキスト、CSP、Tampermonkeyの権限とAPIの挙動を両ブラウザーで確認し、差があれば記録する。直接取得が難しい場合に限り、ページ自身が取得する応答を利用できるか、画面動作や取得タイミングへの影響を含めて検討する。アクセス制限の回避は行わない。評価履歴を利用できる経路が確認できるまで、実口座向けグラフの実装は保留する。入出金明細の直接取得はMVPの前提にしない。

調査記録に残すのは項目名、型、挙動、架空の例とする。実明細、口座識別子、認証ヘッダーを含む通信記録やHARはコミットしない。

## 2. MVPで実装する処理

| 順序・責務 | 実装内容 | 確認方法 |
|---|---|---|
| 1. 起動・ビルド | 対象ページに限定した `@match` と必要最小限の `@grant` を定義する。TypeScriptのモジュールを単一ファイルにまとめる。Viteとvite-plugin-monkeyを候補に、バンドル結果と両ブラウザーでの起動を確認して採否を決める。 | 同じ配布ファイルを両ブラウザーのTampermonkeyにインストールし、対象ページで起動する。実行時のCDNや外部スクリプトに依存しない。 |
| 2. 取得・正規化 | 評価額の読み取りとCSV読み込みを別々のアダプターにする。検証済みの形式から「評価時点・円評価額」と「反映日・方向・円金額・摘要・取得元」を生成し、取得範囲を別に持つ。CSVから照会期間が分からない場合は取り込み時に利用者が指定する。 | ログイン画面への遷移、形式変更、必須欄の欠損、不正な金額を検知し、対象の入力と原因を表示する。取引行の最初と最後の日だけで履歴範囲を推定しない。 |
| 3. 分類・計算 | 次節の規則を純粋なTypeScriptモジュールに実装する。入力は正規化済みの評価系列、明細、履歴範囲、評価対象の境界。出力は評価時点ごとの系列、集計値、算出できない理由。 | SBIの画面やGM APIを使わず、架空のデータで受入例を検証できる。 |
| 4. 表示 | 既存グラフの下に「運用成績（UserScript）」パネルを追加する。評価額・入出金調整後の基準額・累積運用損益の3系列を同じグラフに表示し、損益単独のグラフも表示する。 | 最新の取得評価額と評価日、集計開始日と開始評価額、累計外部入金・出金・純入金、累積運用損益がグラフと一致する。対象期間、未分類件数、欠損・エラーの理由が読み取れる。 |

MVPは一度の集計につき評価系列と1件のCSVをメモリ上で扱い、再読込時は再取得する。同じCSVの選び直しは入力の差し替えとする。UIはShadow DOMでスタイルを分離し、必要な場合に限りDOM再生成を監視する。既存グラフの内部状態には依存しない。表示するグラフやCSV解析にライブラリを採用する場合は、実データの粒度・形式とバンドルサイズをもとに選ぶ。

### GitHubからのインストール

利用者はGitHubリポジトリのREADMEから、次の手順で利用を開始できるようにする。

1. 初回のみ、READMEに掲載した各ブラウザーの公式ストアへのリンクからTampermonkeyを導入する。Google Chromeでは拡張機能の詳細で「ユーザー スクリプトを許可」を有効にする手順も案内する。[Tampermonkey公式の設定案内](https://www.tampermonkey.net/faq.php?q=Q209)
2. README冒頭の「インストール」をクリックし、Tampermonkeyの確認画面でスクリプト名と対象サイトを確認してインストールする。[Tampermonkey公式のインストール手順](https://www.tampermonkey.net/faq.php?q=Q102)
3. SBI証券のMy資産を開く。すでに開いている場合は再読み込みし、「運用成績（UserScript）」が表示されれば導入完了とする。

配布にはGitHub Releasesを使う。リリース担当者はタグに対応するソースからビルドし、その版の `@version` を含む `sbi-my-assets-plus.user.js` をリリースに添付する。READMEのリンク先には `releases/latest/download/sbi-my-assets-plus.user.js` で終わる固定URLを使う。利用者は新しい版でも同じリンクを開いて更新できる。[GitHub公式のリリースへのリンク方法](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)

## 3. 損益の計算契約

開始時点を、明細の履歴範囲と評価系列が重なる最初の有効な評価時点とする。開始評価額にはその時点までに反映された入出金が含まれる。各評価時点では、**開始評価の直後から当該評価まで**に反映された明細を数える。日次の終値相当と確認できた場合、開始日分を除き当日分を含める。約定日・受渡日・明細日が異なる場合の対応は、調査で確認した評価への反映基準に従う。

```text
累計純入金額(t) = 累計外部入金額(t) − 累計外部出金額(t)   ［入金額・出金額は正の大きさ］
入出金調整後の基準額(t) = 開始評価額 + 累計純入金額(t)
累積運用損益(t) = 評価額(t) − 入出金調整後の基準額(t)
入出金を除いた資産額(t) = 評価額(t) − 累計純入金額(t) = 開始評価額 + 累積運用損益(t)
```

UIには「入出金調整後の基準額」と表示する。集計開始が口座開設より後になるためである。後続の期間指定でも、選択した両端の評価額の差から、その間の純入金額を引く。

| 明細の意味 | 純入金額への反映 |
|---|---|
| 外部銀行からの入金、カード積立、ポイント投資 | 対象資産に入った額を加算。積立に伴う口座内振替・買付との重複を除く。ポイントは原則流入とし、円換算額と反映先を確認する。 |
| 外部銀行への出金 | 対象資産から出た額を減算する。 |
| 対象内の売買、両替、積立用資金振替 | 算入しない。 |
| 配当・分配金・利金、税・手数料 | 対象内で受払いされた分は評価額に反映されるため、損益に別途加減しない。 |
| 商品口座・連携預金との振替 | 両端が対象内なら算入しない。境界を越える場合は対象に入る向きを入金、出る向きを出金とする。 |
| 摘要や境界が不明 | 未分類として件数・対象日を表示し、影響する時点の基準額と損益を算出保留にする。 |

実在する評価時点だけを描画する。評価額の欠損はグラフで欠測として示す。明細の履歴に空白があれば、その区間をまたぐ累積値は算出できない。取引がなかったことを確認できた期間だけ純入金ゼロとして扱う。

### 計算と表示の受入例

| 架空の入力 | 期待する結果 |
|---|---|
| 初日の評価額100万円に同日入金10万円が反映済み。翌日に20万円を入金し、評価額が123万円 | 初日の損益は0円。翌日の純入金は20万円、基準額は120万円、損益は+3万円。 |
| 上例の翌日に5万円を出金し、評価額が118万円 | 累計出金は5万円、累計純入金は15万円、基準額は115万円。累積損益は+3万円のまま。 |
| 対象内で配当1,000円を受け取り、税200円を支払い、評価額が800円増加 | 純入金の変化は0円、損益は800円増加。 |
| 金口座へ2万円を振替 | 金が評価対象外なら外部出金2万円、対象内なら外部出金0円。境界未確認なら分類を保留。 |
| 評価額のみの月、明細取得済みで取引ゼロの月、未分類明細がある月 | 順に「履歴不足」、純入金0円、「未分類」を区別し、算出保留中も取得済みの評価額は確認できる。 |

## 4. MVPのリリース判定

- 上記の計算例をユニットテストで検証し、匿名化・架空入力で取り込みから2つのグラフの表示まで通す。
- Windows 11のFirefoxとGoogle Chromeそれぞれで、スクリプト未導入の状態から実際のGitHub READMEの手順をたどる。「インストール」リンクでTampermonkeyの確認画面が開き、承認後にMy資産でパネルが表示されることを確認する。利用者側でのクローン、ビルド、コードの貼り付けは不要とする。
- 両環境で通常ログイン、手動更新、CSV取り込み・再選択、グラフ表示、セッション切れ、画面を往復した際の表示を確認する。パネルは1つだけ表示され、既存の画面操作を妨げず、スクリプト無効化後の再表示で元の画面に戻る。
- ログインと多要素認証は利用者が行う。認証情報・Cookie・トークンの独自取得や保存、注文・売買・出金操作、テレメトリーを実装しない。通信先とログを確認し、資産情報を外部へ送信せず、明細をログに残さないことを確かめる。
- 各ブラウザーについて、検証したブラウザーとTampermonkeyのバージョン、インストール・更新手順を記録する。

## 5. MVPの後に実装すること

1. **履歴の蓄積と復元**。GMストレージの容量・速度・永続性と複数タブでの競合を実測し、必要ならIndexedDBを選ぶ。金融データに限定した元データ、正規化結果、取得元・日時・範囲、分類修正、スキーマ版を保存する。期間の重なる取込は既存履歴にマージし、訂正を反映する。取引IDがなければ行の出現回数も照合する。同日・同額・同種別の正当な2件、同じ明細の再取込、過去期間の保持、同時更新、バックアップからの復元を受入例とする。エクスポート時は金融情報を含むことを表示する。
2. **明細取得と分類の改善**。調査で利用可能と確認した読取経路から、更新操作で入出金履歴も取得する。CSVは過去分の追加・取得失敗時の代替として残す。未分類明細の確認・手動修正後に該当期間を再計算する。
3. **期間別の分析**。期間選択、月別・年別損益、XIRRの順に拡張する。TWRは外部入出金の前後で評価額を特定できる粒度か検証してから採否を決める。独自タブ、資産クラス別分析、ベンチマーク比較、公式の実現損益等との突合は追加候補とする。
