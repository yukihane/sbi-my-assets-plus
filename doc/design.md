# SBI証券 My資産 運用成績可視化ブラウザー拡張機能の開発

## 1. 背景・目的

SBI証券の「My資産」では資産評価額の時系列推移を確認できるが、外部口座との入出金が考慮されていないため、資産の増減が資金投入によるものなのか、投資による運用損益なのかを区別できない。

そこで、外部との資金移動を考慮した実質的な運用損益を計算し、時系列グラフとして可視化するブラウザー拡張機能を開発したい。

独立した資産管理アプリケーションを開発するのではなく、**SBI証券のMy資産画面そのものを拡張し、標準機能に不足している運用分析機能を補完する**ことを目的とする。

## 2. 前提条件

- 利用環境はWindows 11およびFirefox。
- 当初はFirefox向けの拡張機能として開発する。
- 将来的なChrome対応を妨げない設計が望ましい。
- SBI証券へのログインや多要素認証はユーザーが通常どおり行う。
- 認証済みブラウザーセッションを利用してデータを取得する。
- 外部サーバーを必要とせず、ブラウザー内で処理を完結させる。
- 個人利用を前提とする。
- 株式の注文、売買、出金などの機能は一切実装しない。

## 3. 実現したい機能

### 3.1 資産推移の可視化

最低限、以下の時系列データを同じグラフ上に表示したい。

- 資産評価額
- 集計開始時点の資産評価額＋累積純入金額
- 実質的な累積運用損益

資産評価額と累積純入金を考慮した基準線を比較することで、資産増加のうち、どの程度が運用益によるものなのかを直感的に把握したい。

実質運用損益単独のグラフも表示したい。

### 3.2 集計指標

- 現在の資産評価額
- 集計開始時点の資産評価額
- 累計外部入金額
- 累計外部出金額
- 累計純入金額
- 累積運用損益
- 指定期間内の運用損益
- 年率換算収益率（XIRR）
- 時間加重収益率（TWR）

XIRRおよびTWRは後続フェーズでの実装でもよい。特にTWRは資産評価額の取得粒度によって正確に算出できない可能性があるため、必要なデータが揃っているか検証すること。

### 3.3 UI

My資産の既存画面に分析機能を追加したい。

以下の実装方式を検討すること。

1. 既存の資産推移グラフの下に独自グラフを追加する。
2. My資産の既存ナビゲーションに「運用成績」などの独自タブを追加する。
3. 既存の資産推移グラフに、純入金額や実質運用損益の系列を追加する。

既存画面の構造を調査し、実装容易性、保守性、UIの自然さを評価して決定すること。

既存グラフの内部状態や描画ライブラリへの過度な依存は避けたい。既存グラフの置き換えや、独自グラフの追加でも構わない。

MVPでは既存の資産推移画面に独自グラフを追加するだけでもよい。

最終的には、SBI証券にログインしてMy資産を開けば、通常の資産確認と同じ流れで運用成績を確認できるようにしたい。

## 4. 調査済みの事項

### 4.1 資産評価額の取得

SBI証券のMy資産には、過去の資産評価額を表示する資産推移グラフが存在する。

公式の操作ガイドを調べた範囲では、この時系列データをCSVなどで一括ダウンロードする機能は確認できなかった。

一方、Firefoxの開発者ツールでネットワーク通信を調査したところ、以下の内部APIが見つかった。

```http
GET /account/api/assets/valuations
```

確認できた情報：

- HTTPステータス：200 OK
- Content-Type：application/json
- 開発者ツール上のデータサイズ：約941KB

このAPIに過去の資産評価額の時系列データが含まれている可能性が高い。

ただし、レスポンスの実データについてはまだ詳細に調査していない。

以下を調査する必要がある。

- 正確なリクエストURLおよびクエリパラメーター
- レスポンスのJSONスキーマ
- 取得可能な期間
- データの粒度（日次・週次・月次）
- 資産クラス別の評価額の有無
- 預り金の扱い
- 外貨建て資産の扱い
- iDeCoの扱い
- 連携銀行口座の扱い
- 金・銀・プラチナの扱い
- 認証済みページからのfetchで取得できるか

公式公開APIではなく、SBI証券のWebアプリケーション内部で使用されているAPIである点に注意すること。

### 4.2 入出金履歴

SBI証券の円貨入出金明細は公式機能でCSVダウンロード可能である。

サンプルファイルを取得済み。

```text
DetailInquiry_20261125184343.csv
```

対象期間は2024年11月26日から2026年11月25日までの約2年間。

必要であればユーザーにファイル提供を依頼すること。

このCSVには銀行口座との入出金だけではなく、以下の取引も含まれる。

- クレジットカード積立
- 配当金・利金
- 投資信託積立用資金振替
- 譲渡益税
- ポイント利用
- 商品取引口座間の資金振替
- その他の取引

したがって、単純に入金総額と出金総額を差し引いても、外部資金の純流入額にはならない。

CSVの実データを解析して、取引種別の分類ルールを作成する必要がある。

また、入出金明細画面についても、資産推移画面と同様に内部APIが存在しないか調査すること。

最終的には手動CSVダウンロードを必要とせず、ブラウザー拡張機能から直接取得できることが望ましい。

ただし、CSVインポート機能はフォールバックおよび過去データの取り込み手段として残したい。

### 4.3 その他の公式CSV

SBI証券には以下のデータの公式CSVダウンロード機能が存在する、または利用できる可能性がある。

- 保有証券
- 実現損益
- 配当金・分配金履歴
- 約定履歴
- 譲渡益税明細

これらは銘柄別分析や計算結果の検証には有用だが、過去の資産評価額を直接取得できるわけではない。

約定履歴と外部の株価データから資産評価額の推移を再構築する方法もあるが、株式分割、為替、配当、投資信託の基準価額などへの対応が必要になるため、今回の主目的には過剰な実装となる。

原則として、SBI証券が計算済みの資産評価額の時系列データを利用する方針とする。

## 5. 運用損益の計算仕様

時点tにおける累積運用損益を以下のように定義する。

```text
NetContribution(t)
  = ExternalDeposits(t) - ExternalWithdrawals(t)

AdjustedPrincipal(t)
  = InitialAssetValue + NetContribution(t)

InvestmentProfit(t)
  = AssetValue(t) - AdjustedPrincipal(t)
```

ここで、入出金の累計は集計開始時点から時点tまでを対象とする。

口座開設時点まで遡れるとは限らないため、集計開始時点の資産評価額を考慮すること。

また、AdjustedPrincipalは口座開設以来の投資元本とは異なるため、UI上でも混同しない名称にすること。

### 5.1 キャッシュフローの分類

取引を少なくとも以下に分類する。

| 取引種別 | 基本的な扱い |
|---|---|
| 外部銀行口座からの入金 | 外部資金流入 |
| 外部銀行口座への出金 | 外部資金流出 |
| クレジットカード積立 | 外部資金流入 |
| 株式の購入・売却 | 内部取引 |
| 投資信託の購入・売却 | 内部取引 |
| 配当金・分配金 | 運用利益 |
| 譲渡益税・源泉徴収税 | 運用に伴う費用 |
| 手数料 | 運用に伴う費用 |
| 円貨・外貨間の両替 | 内部資金移動 |
| ポイントによる投資 | 原則として外部資金流入 |
| 商品口座間の振替 | 集計対象の境界に応じて判断 |
| 不明な取引 | 未分類として扱う |

配当金や税金などがすでに資産評価額に反映されている場合、運用損益の計算時に重複加算・控除しないこと。

不明な取引を安易に入金・出金として分類しないこと。

将来的にはユーザーが取引分類を確認・修正できるUIを実装したい。

### 5.2 集計対象の境界

ユーザーは以下の金融商品・サービスを利用している、または利用したことがある。

- 国内株式
- 米国株式
- 外貨預り金
- 投資信託
- NISA
- クレジットカード積立
- 金積立
- iDeCo
- SBI証券と連携する銀行預金サービス

集計対象の資産と、入出金として扱う資金移動の境界を一致させることが重要。

例えば、金積立の評価額がMy資産の資産評価額に含まれていない場合、金取引口座への振替を内部資金移動として処理すると計算が合わなくなる。

連携銀行預金についても同様である。

まずは実データからMy資産が集計している資産の範囲を調査し、その範囲に対応したキャッシュフロー分類を行うこと。

### 5.3 時系列データの整合性

- 資産評価額と入出金履歴の取得可能期間が一致するとは限らない。
- 入出金履歴が存在しない期間の運用損益を、正確な値として表示しないこと。
- 資産評価日時と入出金日時の対応を考慮すること。
- 約定日、受渡日、入出金反映日の違いを考慮すること。
- 欠損値を安易にゼロとして扱わないこと。
- データ不足や未分類取引が存在する場合は、UI上で明示すること。
- 評価額の取得粒度より細かい時系列データを、根拠なく生成しないこと。

## 6. 推奨アーキテクチャ

以下の責務を分離する。

```text
SBI証券 My資産 / 入出金明細
         |
    Data Adapter
         |
    Normalization
         |
   Persistent Storage
         |
   Analytics Engine
         |
      Injected UI
```

### Data Adapter

- SBI証券の内部APIへのアクセス
- CSVインポート
- レスポンススキーマの検証
- エラー検出
- 認証セッション切れの検出

### Normalization

- 資産評価額の正規化
- 入出金履歴の正規化
- キャッシュフロー分類
- 重複排除
- 日付・通貨・金額の正規化

### Persistent Storage

- 取得済みの過去データの保存
- 元データの保存
- 正規化済みデータの保存
- データ取得日時および取得元の保存
- ユーザーによる分類修正の保存
- バックアップ・リストア

### Analytics Engine

- 累積純入金額
- 実質運用損益
- 期間別損益
- XIRR
- TWR
- データ整合性の検証

SBI証券固有の処理やブラウザーAPIに依存しない、テスト可能なモジュールとして実装すること。

### Injected UI

- My資産への独自UIのマウント
- グラフ描画
- 集計期間の指定
- データ更新
- 取得状況の表示
- エラーやデータ不足の表示

SBI証券側のHTMLやAPIが変更された場合でも、変更箇所を局所化できる構成を目指すこと。

## 7. データ取得の実装方式

以下の方式を比較検討すること。

### 方式A：内部APIの直接呼び出し

Content Scriptなどから認証済みセッションを利用してAPIを呼び出す。

```javascript
fetch("/account/api/assets/valuations")
```

上記コードは概念例であり、動作確認済みではない。

実際のリクエストに必要なヘッダー、パラメーター、実行コンテキストなどを調査すること。

### 方式B：既存APIレスポンスの捕捉

My資産のページ自身が行うfetchまたはXMLHttpRequestを捕捉して、レスポンスデータを取得する。

追加通信を必要としないメリットがある一方、ページのJavaScript実行コンテキストや呼び出しタイミングへの依存が増える。

### 方式C：CSVインポート

公式機能でダウンロードしたファイルを拡張機能に取り込む。

内部APIが変更された場合のフォールバックとして利用できる。

まずは方式AとCによる実装を想定するが、実際のサイト構造や利用規約、ブラウザーの制約を調査したうえで決定すること。

## 8. My資産へのUI組み込み

以下の技術を検討すること。

- Content Script
- Shadow DOM
- MutationObserver
- SPAの画面遷移検知
- 拡張機能のメッセージパッシング

Shadow DOMなどを使用してSBI証券のCSSと拡張機能のCSSの干渉を抑制する。

SPAである場合は、ページ遷移やDOMの再生成によって拡張機能のUIが消失したり、重複してマウントされたりしないようにすること。

既存グラフの直接改変が容易かどうかについては、実際のグラフ描画ライブラリを調査してから判断すること。

独自に追加・加工した数値については、SBI証券の公式表示と区別できるようにすること。

以下は推奨案であり、必須要件ではない。

| 用途 | 候補 |

実装開始前に各ライブラリの現在の状況を確認し、Firefoxとの互換性、保守性、依存関係を評価すること。

## 10. データの永続化

SBI証券の入出金明細には取得可能期間の制限があるため、取得済みのデータを継続的に蓄積する必要がある。

新たに取得したデータで全件上書きする設計は避けること。

- 取得済みデータとのマージ
- 重複排除
- 過去データの保持
- データの訂正への対応
- スキーマのバージョン管理
- JSON等によるエクスポート・インポート
- バックアップ・リストア

同日・同額・同種別の取引が複数発生する可能性があるため、安易な複合キーによる重複排除で正当な取引を削除しないようにすること。

## 11. セキュリティ要件

金融資産情報を取り扱うため、以下を必須とする。

- ログインID・パスワードを取得・保存しない。
- Cookie、認証トークン、セッションIDを独自に保存しない。
- ログイン操作を自動化しない。
- データ取得は当初、ユーザーによる明示的な操作を起点とする。
- 必要最小限のホスト権限のみを要求する。
- 注文、売買、出金などの操作を実装しない。
- 外部サーバーへの金融資産情報の送信を行わない。
- テレメトリーを実装しない。
- 外部CDNから実行時にJavaScriptを取得しない。
- デバッグログに機密情報を出力しない。
- 実際の金融資産情報をGitリポジトリにコミットしない。
- テストには匿名化済みまたは架空のデータを使用する。
- 拡張機能が無効化された場合はSBI証券の元の画面に戻ること。

IndexedDBは自動的に暗号化されるわけではないため、保存データやバックアップファイルの取り扱いにも注意すること。

また、内部APIのプログラム利用に関するSBI証券の利用規約については未確認である。実装前に確認し、アクセス制限やセキュリティ機構を回避するような実装は行わないこと。

## 14. まず取り組んでほしいこと

現時点ではSBI証券の内部APIや画面構造に未調査の部分が多いため、完成形を想定した大規模な実装をいきなり開始しないこと。

特に、以下の3点を優先すること。

1. 資産推移APIのレスポンス構造を特定する。
2. 入出金履歴をプログラムから取得できるか確認する。
3. My資産の既存画面に独自グラフを安全かつ保守性の高い方法で組み込めるか確認する。

調査結果、設計上の決定事項、未解決事項はリポジトリ内のドキュメントに記録すること。

## 実装方式の変更：WebExtensionsからUserScriptへ

配布・インストール・更新の容易さを重視し、独立したブラウザー拡張機能ではなく、UserScriptとして実装する方針に変更したい。

### 要件

- Firefox上のViolentmonkeyまたはTampermonkeyで動作すること。
- 可能であれば両マネージャーおよびChromeにも対応すること。
- My資産の既存画面に直接UIを組み込む方針は維持する。
- TypeScriptによるモジュール分割された開発を行う。
- ビルド成果物は単一の `.user.js` ファイルとする。
- 実行時に外部CDNから依存ライブラリを読み込まない。
- 対象ページを `@match` で必要最小限に限定する。
- UserScriptマネージャーの権限も必要最小限にする。

### 技術スタックの変更

WXTに代わり、Viteとvite-plugin-monkey等の採用を検討すること。

React、ECharts、Zod、Papa Parse、Vitestなどについては、従来の候補を維持する。ただし必要性を個別に評価すること。

永続化については、まずGM.setValue / GM.getValueなどのUserScriptマネージャーのストレージAPIを検討すること。容量や性能が不足する場合は別方式を検討する。

### 技術調査

以下をPhase 0の調査項目に追加すること。

- UserScriptの実行コンテキストから認証済みAPIを呼び出せるか。
- ViolentmonkeyとTampermonkeyのAPI互換性。
- CSPの影響。
- Shadow DOMによるUI分離。
- GM Storageの容量、性能、永続性。
- 複数タブからの同時更新への対応。
- 単一のUserScriptへの依存ライブラリのバンドル。
- 配布および更新方法。

データ取得、正規化、永続化、運用損益計算、UIの責務分離は維持すること。将来的にWebExtensionsへ移行する場合でも、ドメインロジックを再利用できる設計としたい。

従来の指示書にあるWebExtensions固有の要件と本変更が矛盾する場合は、本変更を優先すること。
